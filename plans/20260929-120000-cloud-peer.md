# Durable cloud peer (supersedes snapshot-first backup delivery)

User approved 2026-09-29: prioritize an always-available multi-household peer and
future trusted-cloud integrations. Historical backup UI is deferred. The app has never been GA; use a clean initial
schema without prototype migrations or legacy snapshot compatibility.

- Reuse worker auth, household assignments, consent, TURN, WebRTC and Supabase pool.
- Add a durable ordered cloud change stream, as the only cloud data protocol.
- Devices keep a durable encrypted upload outbox and applied cursor, transfer in
  bounded chunks over WebRTC, and merge through existing Store5 conflict handling.
- Include tombstones and receipt bytes. Never advance a cursor on failed apply.
- E2E is opaque to workers. Trusted cloud is encrypted with the service storage key;
  it is the foundation for future separately authorized integrations, not a grant
  of external-service access. No integration endpoints ship in this change.
- Shift Settings to cloud sync and recovery keys; automatic synchronization while
  app is active replaces periodic full backups. Remove the prototype snapshot protocol.
- Validate offline handoff, concurrent edits, deletions, replay after restart,
  ciphertext at rest, isolation, missing keys, and both persistence backends.
- Initial log is retained without unsafe compaction; enforce a storage quota and
  surface exhaustion. Compaction and historical disaster recovery are later work.

## Implementation status

Implemented: separate cloud_entries/cloud_chunks persistence; monotonic commit
sequences under the household database lock; durable device outbox/cursor; Store5
merges with tombstones and receipt repair; five-second foreground synchronization;
cloud-sync Settings and explicit trusted consent. Initial schemas include cloud
state; no additive upgrade, prototype import, or legacy snapshot flow is retained.

Integration boundary: trusted cloud stores service-decryptable change batches.
It does not yet expose a materialized entity query API, MCP tools, third-party
credentials, or integration authorization. Those are future features requiring
explicit per-integration scopes and Store5-based processing.

PostgreSQL live acceptance passed both modes with TURN, nonempty-device catch-up,
source offline, hard worker restarts, receipts and deletions. Final SQLite, JVM and
platform validation results are recorded in the completion response.
