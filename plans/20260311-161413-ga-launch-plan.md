# GA Launch Plan

Date: 2026-03-11

## Status

This document tracks the work required to move from the current dev-only state to a public GA launch.

Current reality:

- the app is still operating as a development build and workflow
- hosted and self-hosted mode selection exist, but hosted mode is still bootstrapped from the same editable server URL field used by self-hosted mode
- reset flows are dev-oriented and not yet framed as production-safe support tooling

## Launch Goals

- ship a clear hosted experience for end users
- preserve the existing self-hosted path without weakening architecture invariants
- make first-launch onboarding deterministic and understandable
- align docs, product behavior, and support/reset workflows with public release expectations

## Locked Constraints

- user data traversal remains WebRTC P2P only
- the signaling server remains control-plane only
- Store5 remains the application-data boundary
- hosted tier and household metadata remain server-authoritative

## Phase 1: Hosted Production Endpoint

Goal: make hosted mode point at a real public deployment instead of behaving like a decorated version of self-hosted development.

Build:

- stand up the production/public hosted signaling and API server
- define the canonical hosted base URL for clients
- update first-launch onboarding so the non-self-hosted option cleanly selects that predefined hosted URL
- remove the current shared-URL behavior for hosted onboarding once the public server exists
- keep manual server URL entry available only where it is intentionally a self-hosted or developer flow

Cleanup note:

- The current onboarding implementation is an intentional temporary dev bridge.
- Today, the non-self-hosted option still uses the same server URL field as self-hosted and then relies on `/api/config` to determine runtime mode.
- Before GA, clean this section up so non-self-hosted launches directly target the predefined public signaling/API server URL without asking end users to understand or edit server endpoints.

Test:

- fresh install selecting hosted always points at the public hosted deployment
- fresh install selecting self-hosted still allows custom server entry
- hosted clients do not accidentally persist or reuse self-hosted development URLs

## Phase 2: Hosted User Experience

Goal: finish the product-facing hosted flow.

Current branch status:

- hosted auth is no longer hidden inside the old developer account section
- settings now has a GA-ready account surface plus a separate developer-tools section
- hosted session loss redirects to a dedicated auth gate and blocks normal navigation until the session is restored
- hosted feature placeholders now reflect `FeatureGate` state instead of silently ignoring tiering

Build:

- replace the developer-account surface with dedicated auth UI
- add account management and sign-out UX
- enforce feature gates in hosted UI
- audit first-launch copy and environment wording so public users never see dev terminology

Test:

- hosted onboarding, auth, and normal navigation work without developer settings
- sign-in, sign-up, upgrade, sign-out, and expired-session recovery are coherent on all shipped platforms

## Phase 3: Release Hygiene

Goal: make resets, debugging, and docs safe and explicit for launch and support.

Build:

- keep one-command fresh-state reset flows for desktop, Android, and iOS simulator development
- document which reset workflows are dev-only versus safe for support use
- audit build flags, bundle identifiers, icons, and environment defaults for GA readiness
- ensure docs clearly distinguish hosted public usage from self-hosted operator setup

Test:

- developers can reliably reset each platform to first-launch state
- release docs match actual first-launch behavior
- no dev-only defaults leak into the public hosted path

## Exit Criteria

- hosted onboarding uses a predefined public server URL
- self-hosted onboarding remains explicit and operator-oriented
- hosted auth UX is no longer hidden in developer settings
- docs reflect shipped launch behavior
- launch builds are reproducible and resettable during QA
