# Releases and versioning

Shilling uses one product version for web, desktop, mobile, and server. The
root `VERSION` file is the source of truth.

## Version numbers

Use `MAJOR.MINOR.PATCH`. Major remains `0` during beta, minor is currently
`1`, and patch increases for any published bug fix, including a fix for only
one target. An Android-only fix after `0.1.0` is `0.1.1`, even if the other
targets stay at `0.1.0`. Previews use tags such as `v0.1.1-beta.1`; stable
releases use `v0.1.1`. There is no fourth public version component.

Android `versionCode` and iOS `CFBundleVersion` are separate, increasing store
build numbers. Increase only the relevant build number for a store upload,
including a rebuild at the same product version.

Run `just set-version 0.1.1` to update all product manifests. Add `--android`
for a Play upload and `--ios` for an App Store Connect upload. For example,
`just set-version 0.1.1 --android --ios` prepares a full mobile release;
`just set-version 0.1.2 --android` prepares an Android-only patch. The command
checks the manifests before and after the update. `just check-version` runs in
TeamCity CI and before self-hosted image publishing. The tag must match the
version at that commit.

## What TeamCity does

| Event | Result |
| --- | --- |
| Push to any branch | `Build Linux-agent targets` runs CI, web, server, Android, Linux desktop, and Windows desktop at the same revision. Package files become TeamCity artifacts. |
| Merge to `main` | The branch chain also deploys the hosted web app to Cloudflare Pages after CI passes. Coolify tracks the hosted server's source separately. |
| Push a `vX.Y.Z` or preview tag | Nothing publishes automatically. Queue a build matrix on the tag, review the artifacts, and explicitly publish the selected targets. |

The single Linux runner works through the branch matrix in a queue. The
`Build all targets` composite also includes iOS and macOS desktop and can be
queued on any branch or tag after the Mac agent is connected. Snapshot
dependencies pin the jobs in a chain to one source revision. Failed jobs fail
the composite. The macOS desktop job consumes the same tested web bundle as
the Linux and Windows desktop jobs.

Android produces a debug APK and an unsigned release AAB. iOS produces an
unsigned app ZIP by default; setting `env.SHILLING_IOS_SIGNED=1` with Apple
signing credentials installed exports an IPA. Linux desktop produces x86_64
AppImage, Debian, and RPM packages. Windows desktop cross-builds an x86_64
NSIS installer on Linux; MSI needs a Windows runner. macOS desktop produces
an unsigned universal DMG for Apple Silicon and Intel. These packages stay in
TeamCity until explicitly published.
The workflows do not yet sign or upload to Play, TestFlight, or desktop stores.

The manual `Self-hosted Release` job consumes the tested server JAR and web
bundle from the same tag. It pushes images to GHCR and creates a GitHub
release. Set `env.SHILLING_RELEASE_TARGETS` on that run to `server,web`
(default), `server`, or `web`. A two-image release includes Compose files. A
one-image release omits Compose files because the other image remains on its
previous version. `env.SHILLING_RELEASE_DRY_RUN=1` builds the selected images
without publishing. The job needs a Linux agent with Docker Buildx and `gh`,
TeamCity `env.GITHUB_TOKEN` for the GitHub release, and a separate
`env.GHCR_TOKEN` classic PAT with `write:packages` for the image push. The VCS
root must watch tags as well as branches. Existing GitHub releases are not
overwritten.

## Full release

1. Run `just set-version X.Y.Z --android --ios`, review the manifest changes,
   and merge them to `main`. Wait for its branch matrix to pass.
2. Tag that tested `main` commit `vX.Y.Z` (or `vX.Y.Z-beta.1`) and push the tag.
3. Queue `Build all targets` on the tag and inspect the artifacts. Until the
   Mac agent is connected, queue `Build Linux-agent targets` and treat the
   release as partial.
4. Complete signing and store upload checks. Queue `Self-hosted Release` on
   the same tag with `env.SHILLING_RELEASE_TARGETS=server,web` to publish both
   images and the Compose files. Attach only ready client packages to the
   GitHub release and list exactly which targets were shipped.

## One-target patch

Increase the shared patch number, passing only the store build-number flag
for an affected mobile target. Merge, wait for the `main` matrix, and tag the
tested commit. Queue the affected target job on that tag. For a server-only or
web-only self-hosted image, run `Self-hosted Release` with the corresponding
`env.SHILLING_RELEASE_TARGETS` value. For a client-only patch, publish the
signed client package through its store or attach the installer to a GitHub
release. Record the target shipped for that tag.

The build matrix is coordinated, but delivery to every store is still manual.
We need the Mac agent, Apple signing and notarization, Android upload signing,
and store upload automation for one-click multi-target releases. Hosted Pages
and Coolify deploy from `main` independently of release tags, so a tag does
not move hosted web and server atomically. A GitHub release currently proves
only the images it lists, not that every client shipped together.
